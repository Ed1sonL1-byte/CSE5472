## 当前判断

优先保留 **LiveCheck：智能合约提款／发款流程的拒绝服务回归测试工具**。核心问题是：在明确的交易 gas、攻击资本和处理次数预算下，其他用户的合法操作或恶意接收行为，能否使一个已有付款资格的正常用户无法按约定收到款项？修复以后，正常用户是否恢复收款，未付款项是否仍可领取？

它适合做成供合约开发者本地使用的 CLI 和 Solidity 测试库，输出可重放测试、JSON 数据和简洁 HTML 报告。技术贡献定位为可复用的专项测试方法与实现，不能预先宣称新的通用漏洞发现算法或优于现有模糊测试器。

候选比较：

| 候选 | 主要优点 | 目前最大的风险 | 判断 |
| --- | --- | --- | --- |
| LiveCheck | 正常用户是否收款容易观察；原版、部分修复、完整修复适合对照演示 | 真实案例的可重现性；不同项目需要适配器；有限测试不能证明永久冻结 | 优先继续验证 |
| PauseCheck | 正常、暂停、恢复三个状态容易构成完整流程 | 暂停时哪些操作应保留取决于项目政策，缺少修饰器不等于漏洞；若干审计对应代码不可公开获取 | 备选 |
| TokenProbe | 特殊 ERC-20 行为容易构造和测量 | 与已有 token-tester 的集成测试和异常 token 库重叠较大 | 暂不优先 |

## 工具必须自行完成的工作

开发者提供一个适配器，描述部署、准备资金、合法提交请求、处理请求、用户应收款项和可用恢复操作。适配器负责业务语义；不应写死漏洞触发序列，也不负责选择测试参数。

工具实现三个模块：

1. **场景生成与运行。** 使用可配置的正常、拒收、消耗 gas 接收合约；选择请求顺序、数量、批量大小和处理预算。状态变化通过公开接口发生。对照运行使用相同正常用户请求和可比较的资金条件。
2. **进度与恢复检查。** 检查用户实际收到的款项及未偿还余额，而不仅是交易成功或队列游标前移。记录失败操作、处理调用数、gas 使用量和恢复操作的权限需求。攻击提交成本、锁定资本、恢复成本分别报告。
3. **失败缩减、导出与版本比较。** 缩减过程中保持请求合法、正常对照可完成和相同故障特征；导出确定性 Foundry 测试，并对原版、部分修复、修复版重放同一场景。报告应给出经过缩减的序列，不承诺数学上最短序列。

最低限度的可复用性要求：接入第三个、未用于调整引擎的合约时，只新增适配器和配置，不修改搜索器、结果判定框架和导出器。记录适配工作量。如果每个合约都必须手写触发漏洞的测试主体，这个设计尚未成为可复用工具。

结果状态区分“发现有边界的阻断”“本轮预算内未发现阻断”“无法判定”。部署失败、正常对照未通过或断言前提不足属于无法判定。适配器中的业务断言可以不同，但不应按已知漏洞版本分支或硬编码攻击顺序。

核心先覆盖接收方失败和接收方消耗 gas 对付款流程的影响；请求积累导致清理成本增长可作为同一框架中的扩展。首版聚焦本地 EVM 合约、有明确领取资格的付款流程和有限的恢复策略。自动理解任意 ABI 的业务语义、跨链、主网实时监控和通用形式化证明均不属于该版本。

## 已完成的小验证

代码：`feasibility/test/Feasibility.t.sol`，无外部 Solidity 依赖。六个断言测试运行通过：

| 测试 | 实际观察 |
| --- | --- |
| 批量付款 + 拒收接收者 | 整批回滚，两个正常接收者均未收到款项 |
| 改成每次只处理一笔 | 前面的正常用户收到款项；随后三次处理均卡在拒收请求，后面的正常用户未收到款项 |
| 隔离失败 + 保留补领余额 | 两个正常用户收到款项；失败款项保留，随后可转至另一接收地址领取，重复领取失败 |
| 暂停后的替代提款入口 | 普通入口被拒绝，替代入口仍实际转出了款项 |
| 共享暂停条件阻断应保留的紧急退出 | 有效正常提款成功；暂停后的紧急提款失败，用户余额仍被记录 |
| 符合声明政策的暂停与恢复 | 暂停时普通提款被拒绝、紧急退出成功；恢复后可再次存取 |

本机复现命令，在项目根目录执行：

```sh
forge test --root exploration/feasibility \
  --use /Library/Frameworks/Python.framework/Versions/3.13/bin/solc \
  --offline -vv
```

使用 Foundry 1.3.2、solc 0.8.36、Cancun EVM 配置。以上全部是自行编写的合成样例与手写测试。测试通过表示观察到了预设故障和修复行为，不代表已经实现自动工具，也不代表复现了真实审计漏洞。当前样例没有验证 gas 消耗型接收者或独立交易 gas 边界。

## Related work 与可用案例

- [Foundry invariant testing](https://getfoundry.sh/forge/invariant-testing?highlight=invariant) 已有随机调用序列、handler 和结束时的退出资金检查；[失败重放](https://getfoundry.sh/forge/replay-testing) 也已经存在。不能把这些通用能力作为本项目首次提出的功能。我们拟复用执行基础，新增付款故障场景、预算控制、进度判定和恢复成本比较。
- [Gas Gauge](https://arxiv.org/abs/2112.14771) 研究 out-of-gas 漏洞分析；因此“检测 gas 过高的循环”本身不是新贡献。提案可将重点放在特定付款工作流中正常用户的进度与修复效果，而非泛化的 gas 扫描。
- [Ethernaut Denial](https://ethernaut.openzeppelin.com/level/20) 是公开教学案例，可用于接收方消耗 gas 的开发校准。需要遵守其 gas 条件并考虑更换 partner 的恢复路径，不作为主要独立评估成果。
- [Hubble 2023 Sherlock #116](https://github.com/sherlock-audit/2023-04-hubble-exchange-judging/issues/116) 描述了 gas 消耗接收者阻断提款，附 PoC。核查[公开源码镜像](https://github.com/sherlock-audit/2023-04-hubble-exchange/blob/main/hubble-protocol/contracts/VUSD.sol)可见，失败调用会记录事件并继续。报告中的整个测试 gas 限额不等价于独立处理交易的限额。因此这是**待独立复现的候选**，不能据此断言单个接收者必然导致永久冻结；若不复现，也应保留为防止误报的对照。
- [FactoryDAO #54](https://github.com/code-423n4/2022-05-factorydao-findings/issues/54) 讨论大量小额存款 receipt 增加提取剩余奖励前的清理成本。由于存在到期后由其他人强制提款的路径，应测量恢复调用数和费用，不能改述成永久冻结。公开[固定提交源码](https://github.com/code-423n4/2022-05-factorydao/blob/db415804c06143d8af6880bc4cda7222e5463c0e/contracts/PermissionlessBasicPoolFactory.sol)尚未在本地运行。
- PauseCheck 的政策依赖可参照 [Compound v2 治理文档](https://docs.compound.finance/v2/governance/)：暂停机制有意保留赎回和还款能力。判定必须来自项目政策，不能将所有暂停期间仍可调用的函数视为漏洞。
- TokenProbe 的重叠对象包括 [token-tester](https://github.com/bEsPoKeN-tOkEns/token-tester)。在提出该方向前，需要找到异常 token 样例和既有集成测试以外的明确增量。

## 评估计划

首先完成公开案例的编译、资金准备与独立重放，再承诺真实项目数量。将教学样例、自建缺陷／修复版本、独立公开项目分组报告，同一项目的不同年份和小变体不充作多个独立项目。

可执行目标：三种不同付款实现的适配器；一组明确标注来源的正常、故障、部分修复、修复版本；至少一个未用于开发测试策略的独立公开项目。Hubble 和 FactoryDAO 都只是目前的候选，未完成接入。若前两周仍找不到可运行的独立案例，需重新评估这个选题，而不是将更多合成版本包装成真实评估集。

公平对照采用相同适配器、动作集合、接收者模板、合法参数范围、进度判定和执行预算的随机测试；区别仅在场景选择策略。多随机种子下报告找到可重放失败的比例、首次发现所需执行次数及时间、正常版本的误报、缩减后序列长度，以及用户收款／恢复成本。小样本报告逐案例结果和原始计数，避免泛化为全体 DeFi 的检出率。

失败结论须限定为：“在指定 gas、请求规模、调度和恢复策略下，该正常用户在 K 次有效处理后仍未收到应付款项。”首先确认同预算的正常对照可以完成，等待条件已满足、余额充足、用户与处理者权限正确、攻击操作可由非特权参与者合法提交。单次 revert、不足以处理正常负载的 gas 配置、测试框架本身耗尽 gas，都不能直接归类为安全漏洞。

攻击必须影响正常用户；恶意接收者单独拒收自己的款项不等于全局阻断。独立交易中计算用户余额变化时，应将发送交易的手续费与付款额区分。缩减结果需要在新部署上重放；修复版既要恢复正常用户收款，也要检查被跳过款项的权益保存和防重复领取。

## 学期工作量与里程碑

以下按 10–12 个项目工作周估算，实际提交日期以 Carmen 为准：

- 第 1–2 周：确认威胁模型与进度标准，完成公开案例预检、适配接口和正常对照。
- 第 3–5 周：实现接收者模板、场景生成、独立处理预算与执行记录。
- 期中：至少两个不同实现接入相同引擎，自动找到一个阻断序列，并展示修复后正常用户收到款项。仅演示手写攻击不满足此里程碑。
- 第 6–8 周：实现保留合法性的缩减与复现导出，接入独立项目，完成版本对比。
- 第 9–12 周：冻结评估设置、运行对照、分析失败与误报，整理安装说明、结果与展示。

最终产物是 CLI、Solidity 接收者／适配库、可重放案例、版本锁定配置及评估报告。成功的课程项目可以是一套经过评价的专项回归测试工具，不依赖发现新的线上漏洞或在所有指标上胜过现有工具。
